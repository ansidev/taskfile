# Requirements: git-cliff-migration

## Introduction

Brief: The release tooling in this repository depends on git-chglog, which was
officially archived in January 2026 with its maintainers endorsing git-cliff as
the successor (kanpal issue TFS-1). While migrating, the scope was extended
(user-approved, 2026-11-14) to also remove changie and let git-cliff own
`CHANGELOG.md` generation entirely, consolidating all changelog tooling on a
single, actively maintained tool.

The release workflow shape is preserved: per-tag fragments in `.changes/`,
a full `CHANGELOG.md`, and a `release:create` flow that generates a release
commit.

**Pilot user story**: As a maintainer of this repository, I want release
changelogs generated by an actively maintained tool (git-cliff), so that the
release workflow continues to work without depending on archived software, and
I no longer need two changelog tools.

## Requirements

### Tooling installation (release:prepare)

1. WHEN `task release:prepare` runs, THE SYSTEM SHALL install git-cliff via
   Homebrew.
2. THE SYSTEM SHALL NOT install git-chglog (removed; project archived).
3. THE SYSTEM SHALL NOT install changie (removed by approved scope extension).

### Per-tag changelog fragments (release:changelog, release:changelog_next, release:batch_changelog)

4. WHEN `task release:changelog -- <version>` runs, THE SYSTEM SHALL generate
   `.changes/v<version>.md` containing only the commits in the range
   `<previous-tag>..<v<version>>`, grouped by conventional-commit type.
5. WHEN the requested tag is the first tag in the repository, THE SYSTEM SHALL
   range from the repository's root commit (the root commit itself is excluded;
   it is non-conventional and filtered).
6. WHEN `task release:changelog_next -- <version>` runs, THE SYSTEM SHALL
   generate `.changes/v<version>.md` from unreleased commits labeled
   `v<version>` (`git-cliff --unreleased --tag`).
7. WHEN `task release:batch_changelog` runs, THE SYSTEM SHALL regenerate
   fragments for every existing `v*` tag in version order, each covering only
   its own range.
8. WHEN fragment tasks run, THE SYSTEM SHALL pass `--strip all` so fragments
   contain only the version section (no document header/footer).
9. WHEN a fragment generation task runs, THE SYSTEM SHALL create `.changes/`
   if it does not exist.

### Full changelog ownership (release:create)

10. WHEN `task release:create -- <version>` runs and `CHANGELOG.md` exists,
    THE SYSTEM SHALL prepend only the new release section to the existing file,
    inserted below the `# Changelog` header
    (`git-cliff --unreleased --tag v<version> --prepend`).
11. WHEN `task release:create -- <version>` runs and `CHANGELOG.md` does not
    exist, THE SYSTEM SHALL create it with the document header plus the new
    release section (`git-cliff --unreleased --tag v<version> --output`).
12. THE SYSTEM SHALL NOT invoke changie anywhere in the release flow.
13. WHEN `release:commit_release` runs, THE SYSTEM SHALL stage only
    `CHANGELOG.md` and the version file (`package.json`), not `.changes/`.

### Configuration (cliff.toml)

14. THE SYSTEM SHALL commit a `cliff.toml` that: groups commits by
    conventional-commit type (Features, Bug Fixes, Performance Improvements,
    Code Refactoring, Documentation, Tests, Styles, Reverts, Continuous
    Integration, Miscellaneous Chores), skips `chore(release)` commits, filters
    non-conventional commits (`filter_unconventional = true`), protects
    breaking commits, and always renders the version section
    (`render_always = true`).
15. THE SYSTEM SHALL use header `# Changelog` and empty footer in `cliff.toml`.

### Non-functional

16. THE SYSTEM SHALL verify against the repository's actual commit history;
    non-conventional commits (currently only "Initial commit") are filtered.
17. THE SYSTEM SHALL not change task names or CLI argument conventions
    (`task release:<task> -- <version>`), preserving the README task table.

## Out of scope

- Fixing the pre-existing `package.json` staging bug: `commit_release` stages
  `package.json` (`VERSION_FILE`) but the repository has no `package.json`, so
  `release:create` fails at the commit step — same behavior before and after
  this migration. (Flagged in TFS-1; fix pending separate approval.)
- Changing the `TAG_PREFIX` or `.changes/` fragment format beyond what
  git-chglog produced.
- CI/release automation beyond the local task workflow.

## Verification evidence

All EARS requirements 1–17 were verified against git-cliff 2.14.2 in a
throwaway clone with throwaway tags on 2026-11-14: first release creation,
incremental `--prepend` insertion (below header, newest first), full
regeneration, per-tag fragment isolation, and fragment header stripping. See
`tasks.md` for the task-level record.
